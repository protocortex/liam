# LIAM as a GBrain-class substrate: target architecture and roadmap

**Date:** 2026-07-31
**Status:** Approved design (roadmap-level), pending per-milestone plans
**Baseline:** tag `v0.1.0` (MVP: bitemporal store, hybrid RRF retrieval, MCP daemon)

## Purpose

Reference: GBrain (Garry Tan's open-source memory layer for AI agents) and its
companion GStack. GBrain is a self-wiring, typed knowledge-graph memory layer:
hybrid retrieval (vector + keyword + typed graph), entity-centric pages
(compiled truth on top, timeline below), tiered enrichment by mention
frequency, overnight self-maintenance (citation repair), and synthesized answers
over retrieval (SOTA LongMemEval). It ships on PGLite.

LIAM's target is the same class of system on a **libSQL** foundation, but as a
**unified bitemporal substrate** that serves *both* AI-agent working memory and
the personal/company-brain use case, rather than a personal-brain only.

This document defines the target architecture and a dependency-ordered milestone
roadmap. Each milestone gets its own brainstorm -> scope -> implement cycle; this
spec is the spine they hang off, not an implementation plan itself.

## What LIAM already has (v0.1.0)

- Bitemporal store (valid/tx time, `live` predicate, `FOREVER`, `supersede`,
  `upsert_by`).
- Hybrid retrieval: FTS + vector + graph fused by RRF, then confidence + decay.
- Community detection (Leiden) over the edge graph (`recompute_communities`,
  `communities`) — present but not yet wired into the daemon (see M5).
- MCP daemon (`liamd`) exposing `remember` / `recall`; GC background tick.
- Pluggable `Embedder` / `Reranker` traits (mock default, local fastembed).

## Foundational decisions (approved)

1. **Unified substrate.** One bitemporal graph holds agent artifacts and
   people/orgs. Entity type is an open dimension, not a schema fork.
2. **Local-first, pluggable LLM.** A new `Llm` trait mirrors the existing
   `Embedder` / `Reranker` abstraction: `mock` default, local (Ollama/candle)
   as the default-real provider, API providers via config. Only extraction
   (M3) and synthesis (M2) depend on it; the rest of the system does not.
3. **Entity/synthesis model = synthesized-node + supersede (Option A).** An
   entity page is an `entity`-kind node whose `content` is the LLM-compiled
   "truth." Recompiling supersedes the prior version, reusing the bitemporal
   `supersede` primitive. The "timeline below" is a live query over
   provenance-linked facts/episodes; entity history falls out of tx-time for
   free. No new storage concept, no second history mechanism.

## Target architecture

### Node model extension

- Add an `entity` node kind and a free-form `entity_type` field
  (`person`, `company`, `concept`, `artifact`, ...). Existing kinds
  (`decision`, `fact`, `symbol`, `episode`) are unchanged.
- Provenance edges link an entity node to the facts/episodes that mention or
  substantiate it (enables both forward citation and backward "what does this
  episode touch" traversal, as in GBrain's bidirectional indices).

### Llm trait

- New trait alongside `Embedder` / `Reranker`; mock default; local default-real;
  API via config. Consumed only by extraction and synthesis.

### Entity pages (Option A)

- Page = `entity` node; compiled truth in `content`, regenerated by superseding.
- Timeline = live query over provenance-linked facts/episodes ordered by valid
  time.
- Dedup/identity on entities reuses `upsert_by` (subject/scope) + RRF matching.

### Ingestion

- Generic `ingest(Episode)` path: raw text/markdown in -> LLM extracts
  entities + relations -> dedup against live nodes -> write nodes/edges with
  provenance.
- Concrete connectors (email, calendar, voice memos, tweets) are pluggable and
  live outside the core; text/markdown is the first and only in-core source.

### Enrichment tiers

- Mention counters on entities drive scheduled promotion: ~3 mentions -> light
  enrichment; meeting or ~8+ mentions -> full pipeline. Never on the hot write
  path.

### Self-maintenance

- Extend the existing GC tick into a maintenance cycle: community recompute
  (lands the clustering work), provenance/citation repair, and re-synthesis of
  stale entity pages. Non-fatal, runs on the GC cadence.

### Answer synthesis

- `recall` gains an optional synthesized-answer mode: RRF retrieve -> assemble
  context annotated with temporal validity -> `Llm` composes a cited answer.
  The existing raw-ranked-hits mode remains the default/other option.

### Deployment

- Stays stdio MCP for now. HTTP + OAuth server and multi-repo / client-pod
  scoping are the final milestone.

## Milestone roadmap (dependency-ordered)

- **M1 — Foundation.** `Llm` trait (mock/local/api) + open entity dimension
  (`entity` kind, `entity_type`, provenance edges). Unblocks everything.
- **M2 — Entity pages + synthesis.** Option A entity pages + synthesized-answer
  `recall` mode. First user-visible GBrain-class payoff.
- **M3 — Ingestion.** Generic LLM extraction path over text/markdown, dedup,
  provenance writes.
- **M4 — Enrichment tiers.** Frequency-driven promotion and scheduled
  enrichment.
- **M5 — Self-maintenance.** GC-tick extension: community recompute (absorbs the
  clusters work), citation/provenance repair, stale-page re-synthesis.
- **M6 — Deployment.** HTTP + OAuth, multi-tenant / client-pod scoping.

## Absorbed / superseded prior work

- The standalone "always-available clusters" design
  (`2026-07-23-always-available-clusters-design.md`) is folded into **M5**
  (self-maintenance). Its two goals still hold: make clustering unconditional
  (remove the Cargo feature gate) and wire `recompute_communities` into the
  maintenance tick. It is no longer delivered as an independent slice.

## Non-goals (this roadmap)

- No commitment to specific comms connectors in-core (pluggable, out of scope).
- No multi-tenant/OAuth work before M6.
- No change to the RRF/decay math beyond adding synthesized-answer assembly.
- Entity-type taxonomy stays open/free-form; no fixed ontology.

## Open risks

- **LLM quality vs. local-first.** Local models may underperform on extraction/
  synthesis vs. API providers; the pluggable trait lets us swap, but M2/M3
  quality bars should be validated against a real provider before declaring the
  local default sufficient.
- **Extraction dedup correctness.** Entity identity resolution (M3) is the
  hardest correctness surface; over-merging collapses distinct entities,
  under-merging fragments them.
- **Re-synthesis cost.** Superseding entity pages on every maintenance tick
  could churn tx-history; M5 needs a staleness threshold, not blind re-synth.

## Next step

Per-milestone cycles, starting with **M1**: a dedicated brainstorm -> scope ->
implement pass. This roadmap is the reference each milestone plan cites.
